# Evaluation

How retrieval quality is measured, and how to reproduce the numbers quoted in the
[main README](../README.md).

## Running it

```bash
# Full pipeline plus each single-retriever baseline, over the same queries
python scripts/evaluate.py --compare

# Write the full report (every metric, per query) as JSON
python scripts/evaluate.py --compare --json eval/report.json

# Show the worst-performing queries
python scripts/evaluate.py --compare --show-failures 5
```

The same harness is available over HTTP:

```bash
curl -s -X POST localhost:8000/evaluate \
  -H 'content-type: application/json' \
  -d '{"compare": true, "k_values": [1, 3, 5, 10, 20]}' | jq
```

`eval/baseline.txt` is the committed output of `scripts/evaluate.py --compare`;
CI regenerates the corpus and asserts it is byte-identical, so the committed
baseline cannot silently drift from the code.

## The test set

`eval/testset.jsonl` is generated by `scripts/make_sample_data.py` and holds **42
labelled queries** over the **20-document** synthetic corpus in `data/sample/`
(25 chunks, **48 gold chunks**). Twelve of the twenty documents are labelled
"core" sources; the other eight are deliberate distractors on adjacent topics, so
a retriever that matches on topic words alone is penalised.

Each record looks like this:

```jsonc
{
  "query": "Why does the Transformer need positional encodings?",
  "anchor": "Because recurrence is removed, the model has no inherent notion of token order, so sinusoidal positional encodings are added to the input embeddings.",
  "doc_hint": "attention"
}
```

A coverage query, whose answer spans several passages, carries several anchors:

```jsonc
{ "query": "...", "anchors": ["...", "..."], "doc_hints": ["hybrid_eval_2023", "rag_survey_2023"] }
```

## Anchor labelling (the one convention to know)

**A label is an exact sentence from a source document, never a chunk id.**

At evaluation time `resolve_anchors` finds whichever chunk *currently* contains
that sentence and treats it as gold. This matters because chunk ids are an artefact
of the chunking parameters: a label that hard-codes `attention_2017::3` silently
points at the wrong text the moment `RAG_CHUNK_WORDS` changes, and the test set
would keep "passing" while measuring nothing.

Consequences:

- Labels survive re-chunking, so the test set is stable across chunk-size tuning.
- An anchor that no longer appears anywhere (the document changed, the sentence
  was split differently) is reported as **unresolved** and skipped, not counted as
  a miss. A stale label is an evaluation bug, not a retrieval failure.
- `index_coverage` reports `n_queries`, `n_labels`, `unresolved_queries` and
  `avg_gold_per_query`, so a test set that has drifted away from the corpus is
  visible instead of quietly scoring zero.

## Metrics

For one query with gold set `G` and a retrieved ranked list `r`:

| Metric       | Definition                                                                 |
| ------------ | -------------------------------------------------------------------------- |
| Recall@K     | \|top-K ∩ G\| / \|G\|                                                      |
| Hit@K        | 1 if any gold chunk is in the top K, else 0                                |
| Precision@K  | \|top-K ∩ G\| / K                                                          |
| nDCG@K       | DCG@K / IDCG@K, with `DCG@K = Σ gain_i / log2(i+1)`, gain = 1 for gold     |
| MRR          | 1 / rank of the first gold chunk                                           |
| MAP@K        | mean over queries of average precision@K                                   |

`Recall@K` differs from `Hit@K` only for the coverage queries (multiple gold
chunks); for single-gold queries they coincide. `MRR` is the metric to watch for
"is the best answer first", which is what a reranker is supposed to improve.

## Current results

Committed in [`baseline.txt`](baseline.txt), using the dependency-free backends
(`hashing-blake2b-512` embedder, FAISS index, lexical reranker, RRF fusion):

| pipeline               | Recall@1 | Recall@3 | Recall@5 | MRR    | nDCG@5 | MAP@20 |
| ---------------------- | -------- | -------- | -------- | ------ | ------ | ------ |
| BM25 only              | 0.8095   | 0.9762   | 0.9762   | 0.9365 | 0.9345 | 0.9196 |
| dense only             | 0.7262   | 0.9762   | 0.9881   | 0.8770 | 0.8952 | 0.8599 |
| hybrid (RRF, no rerank)| 0.8095   | 0.9762   | 0.9881   | 0.9365 | 0.9389 | 0.9181 |
| **hybrid + rerank**    | **0.8095** | **0.9762** | **0.9881** | **0.9365** | **0.9389** | **0.9181** |

### What these numbers do and do not say

- **Hybrid ≥ every single retriever on every metric.** BM25 alone is already
  strong on this corpus (the documents use distinctive terminology); the dense
  proxy adds recall@5 coverage; fusion keeps the rank-1 precision of the better
  retriever while taking the coverage of the other. That is the headline.
- **The reranker is neutral here, and that is reported honestly.** With a lexical
  proxy embedder and a lexical fallback reranker there is no non-lexical signal to
  add, so at the shipped neutral weight hybrid + rerank ties hybrid without it.
  Sweeping the weight on this set confirms it: `0.0`–`0.1` ties the fused order,
  and `0.6`–`0.75` buys `+0.012` recall@1 at the cost of `-0.003` nDCG@5 and
  `-0.007` MAP@20 — a rank-1 swap, not a better ranking. The default is the
  conservative neutral value, not a flattering one.
- **The reranker's payoff is the cross-encoder, not the fallback.** A real
  cross-encoder scores query and passage jointly, which is information neither
  retriever nor the lexical reranker has. That path is exercised by the scheduled
  [`models.yml`](../.github/workflows/models.yml) workflow, which installs
  Sentence Transformers and FAISS and re-runs this harness.
- **This is a regression harness, not a benchmark.** The corpus is synthetic and
  small; quote these numbers as "the pipeline behaves as designed", not as state
  of the art.

## Adding queries

Edit `scripts/make_sample_data.py` (the source of truth) rather than
`eval/testset.jsonl` — CI asserts the corpus and test set regenerate
byte-identically.

1. Add an entry to `QUERIES` with `query`, `doc_hint`, and either:
   - `"anchor": "<exact sentence copied from the document>"`, or
   - `"fragments": [["<doc_key>", "<exact sentence>"], ...]` for a coverage query.
2. Regenerate and re-evaluate:

   ```bash
   python scripts/make_sample_data.py
   python scripts/ingest.py --sample --rebuild
   python scripts/evaluate.py --compare --json eval/report.json
   ```

3. Commit the regenerated `data/sample/`, `eval/testset.jsonl` and
   `eval/baseline.txt`.

The anchor must match the document text exactly (whitespace is normalised, case is
folded). If it does not, `index_coverage` will report it as unresolved rather than
scoring it — check the `unresolved_queries` count after adding a query.
